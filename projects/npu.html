NPU 온프레미스 LLM 추론 서비스

벤더가 지원하지 않는 최신 33B 모델을 국산 NPU에 직접 포팅하고, 운영 중인 서비스를 멈추지 않은 채 기능을 늘려 온 과정입니다.

기간
2026.06 ~ 운영 중
역할
포팅, 최적화, 배포, 운영 단독 수행
환경
Rebellions ATOM-Max 8장 (장당 15.7GiB)
기술
optimum-rbln, rebel-compiler, vLLM + vllm-rbln, EXAONE 4.5 VL, bge-m3, PyTorch
12 / 12원본 대비 greedy 출력 일치 (33B)
76.5 tok/sbatch 4 처리량, 32K 컨텍스트
13.5s → 2.35s이미지 10장 대화 첫 토큰 지연
3.4배임베딩 처리량 (10.8 → 37 chunks/s)

OVERVIEW서비스 구성

NPU 8장에 서비스 세 개가 함께 올라가 있습니다. 33B 모델은 8장에 나눠 올리고, 임베딩 서비스는 그중 4장을 함께 씁니다. 번역기는 NPU 서비스의 호스트 CPU를 방해하지 않도록 스레드를 제한해 CPU에서 돌립니다.

01EXAONE 4.5 33B 포팅

문제

사내 NPU에서는 EXAONE 3.5까지만 돌았습니다. 4.5는 변환 클래스도, 서빙 엔진 등록도 없었고, 멀티모달 모델이라 텍스트 모델로 바로 불러올 수도 없었습니다.

접근

4.5는 하이브리드 슬라이딩 윈도우, 위치 인코딩이 없는 글로벌 레이어, QK-norm, 순수 post-norm으로 3.5와 계산 그래프부터 다릅니다. 비슷한 구조를 가진 공개 구현을 참조해 세 차이를 각각 구현한 독립 모듈을 만들었고, 벤더 패키지 코드는 한 줄도 고치지 않았습니다. 컴파일러가 양자화와 슬라이딩 윈도우가 함께 있는 그래프를 처리하지 못한다는 것을 먼저 확인하고, 품질과 32K 컨텍스트를 지키려고 bf16 무양자화를 택했습니다.

검증

검증 방법 자체를 먼저 믿을 수 있게 만들었습니다. 지원 모델의 작은 버전으로 원본과 NPU 결과가 16/16 일치하는 것을 확인한 뒤, 같은 절차로 실제 33B 가중치를 비교해 greedy 출력 12/12 일치를 확인했습니다.

돌아가는 것과 맞게 답하는 것은 다릅니다. 배포 후 400토큰이 넘는 입력에서만 답이 무너졌습니다. 포팅 버그로 의심하기 전에 원본 모델도 같은 길이에서 무너지는 것을 보여 원인을 좁혔고, 설정을 옮기는 과정에서 RoPE 기준값이 비어 있던 것을 찾아 고쳤습니다. 추출 도구에 자동 보정을 넣어 재발을 막았습니다.

02비전 인코더 포팅과 무중단 교체

목표

텍스트만 처리하던 서비스를 같은 포트, 같은 모델 이름으로 이미지까지 읽는 모델로 바꾸는 것. 앱은 아무것도 바꾸지 않습니다.

접근

비전 인코더 구조를 분석해 기존 래퍼를 그대로 쓸 수 없는 부분을 찾아 직접 구현하고(약 2,400줄), 컴파일된 디코더와 비전 모듈을 재컴파일 없이 조립했습니다. 교체는 아래 절차로 자동화했습니다.

결과

비전 출력은 기준값과 코사인 0.9999, 기존 텍스트 응답은 바이트 단위로 동일해 회귀 0. 이후 재컴파일 없이 한 요청에 이미지 10장까지 늘렸습니다.

03비전 임베딩 캐시로 첫 토큰 지연 5.7배 단축

문제

앱은 매 턴 대화 전체를 다시 보내서, 이력에 있는 이미지가 턴마다 다시 인코딩됐습니다. 같은 요청을 두 번 보내도 13.5초로 똑같았습니다.

분석

프리픽스 캐싱이 설정이 아니라 설계상 이중으로 막혀 있다는 것을 소스에서 확인했습니다. 지연을 장수와 해상도별로 나눠 재 보니 장당 비용의 80%가 비전 인코딩이었고, "프리필이 대부분"과 "해상도를 낮추면 빨라진다"는 두 추측을 철회했습니다.

해결

비전 인코더 출력은 앞 문맥과 무관하게 이미지만으로 정해진다는 점을 이용해, 이미지 바이트 해시를 키로 하는 캐시를 인코더 호출 지점에 씌웠습니다. 서빙 엔진과 컴파일된 그래프는 건드리지 않았습니다.

빨라 보였지만 버린 방안. 비전 인코더를 남는 카드 다섯 장에 복제해 병렬로 돌리는 구조는 모든 검증을 통과했고 CPU 모의 실험에서 4.9배가 나왔지만, 실제 NPU에서는 이득이 0이었습니다. 런타임 호출이 파이썬 GIL을 쥔 채 동기로 돌아 스레드가 직렬화된 것이 원인이었고, 카드 메모리만 차지하는 구조라 배포에서 뺐습니다.

04임베딩 처리량 3.4배

문제

batch 4로 컴파일한 임베딩 모델이 초당 11청크에 머물렀습니다.

원인

모델 자체는 이미 배치를 지원했고, 서빙 엔진 상류 세 곳이 요청을 한 번에 하나씩만 흘려보내고 있었습니다.

결과

세 곳을 임베딩 모델에만 적용되도록 고쳐 10.8 → 37 chunks/s. 길이를 섞은 입력으로 배치 경로를 자극하는 검증 도구를 만들어, 단건과 배치와 동시 요청 모두 기준 벡터와 코사인 1.00000000을 확인했습니다. 6월 23일부터 재시작 없이 가동했습니다(7월 말 기준).

05음성 모델 이식 타당성과 NPU 결함

회의록 기능에 쓸 음성 모델을 NPU로 옮길 수 있는지 문서가 아니라 실제 컴파일과 실행, CPU 대조로 판정했습니다. 운영 중인 서비스를 건드리지 않도록 컴파일은 호스트에서만 했습니다.

모델판정근거
Whisper large-v3포팅 불필요네이티브 지원, 실시간 70.5배, 전사 결과 CPU와 일치
wav2vec2포팅 불필요세 종류 모두 전사 결과 CPU와 일치
pyannote절반만 이식화자 임베딩만 NPU에서 179배, 세그멘테이션은 CPU로 충분

가장 중요한 발견. 이 NPU에서 LSTM은 오류 없이 틀린 값을 냅니다. 실제 크기에서 CPU 대비 코사인 0.007까지 떨어지지만, 작은 크기에서는 1.0000이라 작은 예제로 확인하고 넘어가면 놓칩니다. 같은 크기의 다른 연산을 대조군으로 함께 돌려 NPU 전체가 아니라 LSTM 고유의 문제로 좁혔습니다.
