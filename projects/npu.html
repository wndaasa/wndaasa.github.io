01EXAONE 4.5 33B 서빙

Rebellions ATOM-Max 2장, 총 8칩에 EXAONE 4.5 33B와 bge-m3 임베딩을 함께 올렸고, AI 협업 문서 플랫폼이 OpenAI 호환 API로 호출합니다.

1-1텍스트 디코더 포팅

NPU 서버에서는 EXAONE 3.5까지만 지원했었습니다. 4.5는 벤더 변환 라이브러리(optimum-rbln)에 변환 클래스가 없고 서빙 엔진(vllm-rbln)에도 등록되지 않았으며, 멀티모달 모델이라 텍스트 모델로 바로 불러올 수도 없었습니다.

4.5는 하이브리드 슬라이딩 윈도우, 위치 인코딩이 없는 글로벌 레이어, QK-norm, 순수 post-norm으로 3.5와 계산 그래프부터 다릅니다. 하이브리드 슬라이딩 윈도우는 gemma3, QK-norm은 qwen3에 기 구현되어 있는 코드를 참고해 4.5용 모델 코드를 별도 모듈로 작성했습니다. 벤더 라이브러리 코드는 수정하지 않아, 버전이 바뀌더라도 포팅이 깨지지 않도록 했습니다. 공개 체크포인트는 이미지까지 읽는 멀티모달 모델이라, 텍스트 디코더 가중치 707개만 골라 텍스트 모델 형식으로 옮겼습니다.

컴파일러가 양자화 연산과 슬라이딩 윈도우가 함께 있는 그래프를 컴파일하지 못했습니다. int8로 정적 컴파일하는 우회도 만들었지만 4,096토큰을 넘는 구간의 정확도를 잃어, 8칩 텐서 병렬(TP8)에 bf16 무양자화로 올려 원본 품질과 32K 컨텍스트를 지켰습니다.

1-2원본 대비 정합성 검증

비교 절차가 맞는지부터 벤더가 지원하는 Qwen3로 확인했습니다. Qwen3 구조의 4층짜리 작은 모델을 무작위 가중치로 만들어 원본(HF, CPU)과 NPU에 같은 10토큰을 넣었고, greedy로 생성한 16토큰이 모두 같았습니다. 같은 절차로 슬라이딩 윈도우 레이어 3개와 글로벌 레이어 1개를 쌓은 EXAONE 4.5 구조의 작은 모델을 비교하자 생성한 12토큰이 모두 같았고, 윈도우 128토큰을 넘는 200토큰 입력에서도 같았습니다. prefill logit의 코사인 유사도는 각각 0.99997과 0.99998이었습니다.

실제 33B는 4 ~ 5,308토큰 길이의 입력 7개를 같은 토큰 ID로 원본과 NPU에 넣고, greedy로 32토큰씩 생성해 비교했습니다. 4개는 32토큰이 모두 같았고, 나머지 3개가 갈라진 지점은 모두 원본에서 1위와 2위 후보의 logprob이 bf16 정밀도에서 같은 값인 곳이었습니다. 원본과 NPU의 상위 5개 후보는 입력별 평균 4.7 ~ 4.9개가 겹쳤습니다.

1-3서빙 엔진 등록과 배포

vllm-rbln에는 import할 때 한 번 실행되는 등록 훅만 넣었습니다. 새 모델 키만 추가하고 실패해도 다른 모델 로드를 막지 않게 감싸, 같은 서버의 기존 모델에는 영향을 주지 않습니다.

TP8, 최대 길이 32,768, 배치 4로 컴파일했고 로드에 41초가 걸립니다. 서빙 엔진으로 측정한 단일 요청의 생성 속도는 19.2 tok/s입니다. NPU의 decode 스텝은 배치 크기와 관계없이 49ms로 일정해서, 동시 4요청이면 합계 73.3 tok/s가 나옵니다.

02이미지 입력 확장

텍스트만 처리하던 서비스를 같은 포트, 같은 모델 이름으로 이미지까지 읽는 모델로 바꿨습니다. 플랫폼 쪽은 수정하지 않았습니다.

2-1비전 인코더 포팅

비전 인코더는 Qwen2.5-VL 계열 구조지만 GQA와 SwiGLU로 바뀌어 있어 벤더의 Qwen 래퍼를 쓸 수 없었고, 이미지 융합은 LLaVA 방식이었습니다. 그래서 전처리는 Qwen2VL 프로세서, 융합과 생성은 슬라이딩 윈도우 디코더 경로로 조합했습니다.

비전 타워의 CPU 레퍼런스부터 컴파일 래퍼, 결합 모델, 서빙 클래스, 등록 모듈까지 작성했고, 컴파일된 디코더와 비전 모듈은 재컴파일 없이 조립했습니다. 비전 출력은 CPU 레퍼런스가 원본과 코사인 1.0000, NPU 실행 결과가 0.9999였고, 기존 텍스트 응답은 플랫폼의 실제 생성 파라미터로 비교해 바이트 단위로 동일했습니다.

요청당 이미지는 1장에서 10장으로 늘렸습니다. 비전 버킷이 이미지 단위라 재컴파일은 필요 없었고, 기존 설정이면 10장이 40,960토큰이라 최대 길이 32,768을 넘어 기동이 실패했습니다. max_pixels를 1,036²로 낮춰 장당 1,369토큰, 10장 13,690토큰으로 맞췄습니다.

2-2교체 절차와 자동 롤백

교체 스크립트가 기존 응답을 기준값으로 저장하고, 기존 서비스를 내린 뒤 새 모델을 띄워 텍스트 회귀, 이미지 동작, 헬스를 자동으로 확인합니다. 하나라도 실패하면 로그를 남기고 이전 모델로 되돌립니다.

2-3비전 임베딩 캐시

플랫폼은 매 턴 대화 이력과 이전 이미지를 최근 10장까지 다시 보내서, 이력에 있는 이미지가 턴마다 다시 인코딩됐습니다. 같은 이미지 10장이 든 요청을 두 번 보내도 첫 토큰 지연이 13.5초로 같았습니다.

프리픽스 캐시는 서빙 플러그인이 멀티모달 모델이면 끄고, 슬라이딩 윈도우 모델이면 한 번 더 끄는 이중 제약이라 설정으로 켤 수 없었습니다. 최신 안정 버전의 해당 코드도 같아 업그레이드로도 풀리지 않습니다. 지연을 장수와 해상도별로 재 보니 장당 1.34초 중 1.08초가 비전 인코딩이었고, 비전 그래프는 실제 패치 수와 관계없이 고정 크기로 실행돼 해상도를 낮춰도 줄지 않았습니다.

비전 인코더 출력은 앞 문맥과 관계없이 이미지만으로 정해지므로, 이미지 픽셀 해시를 키로 인코더 출력을 최대 64장까지 저장하는 LRU 캐시를 인코더 호출 지점에 넣었습니다. 서빙 엔진과 컴파일된 그래프는 건드리지 않았습니다. 같은 이미지 10장을 다시 보낼 때 첫 토큰 지연은 13.5초에서 2.35초로 줄었습니다.

03bge-m3 임베딩 서빙

3-1배치 스케줄러 패치

배치 4로 컴파일한 임베딩 모델이 초당 약 11청크에 머물렀습니다. 모델 forward와 pooling은 이미 여러 요청을 한 번에 처리할 수 있었는데, 서빙 엔진 상류 세 곳이 요청을 하나씩만 흘려보내고 있었습니다. 스케줄러는 prefill을 한 스텝에 하나씩만 보냈고, 러너는 여러 prefill을 예외로 처리했으며, prefill 준비 함수는 단일 요청 전용이었습니다.

세 곳을 임베딩 같은 pooling 모델에만 적용되도록 고쳐 디코더 경로에는 영향을 주지 않았습니다. 여러 요청을 공통 길이로 패딩해 쌓을 때는 행 순서를 요청 ID 순서에 맞췄습니다. 어긋나면 오류 없이 벡터가 뒤섞이기 때문입니다.

처리량은 초당 10.8청크에서 37청크로 3.4배가 됐습니다. 길이를 일부러 섞은 입력으로 배치 경로를 자극하는 검증 도구를 만들어, 단건, 배치, 동시 요청 모두 기준 벡터와 코사인 1.00000000을 확인했습니다.

04트러블슈팅

4-1400토큰이 넘는 입력에서 답이 무너짐

문제

배포 후 400토큰이 넘는 입력, 특히 RAG 질의에서만 답이 무너졌습니다.

원인

처음에는 포팅 버그로 의심했지만, NPU를 거치지 않은 원본 실행에서도 같은 길이에서 똑같이 무너져 포팅 문제가 아님을 먼저 확인했습니다. 원인은 체크포인트에서 설정을 옮길 때 최상위 rope_theta가 비어 있던 것이었습니다. 4.5는 실제값 1,000,000을 rope_scaling 안에만 두는데, RoPE는 최상위 값으로 주파수를 계산해 위치가 작은 짧은 입력만 멀쩡했습니다.

해결

값을 보정하고 재컴파일했습니다. RoPE 테이블은 컴파일할 때 그래프에 들어가기 때문입니다. 가중치 추출 도구에 자동 보정을 넣어 재발을 막았습니다.

결과

390토큰과 3,020토큰 RAG 입력 모두 정상으로 답했습니다.

4-2구조화 출력 요청이 섞인 배치에서 엔진이 죽음

문제

구조화 출력(structured outputs) 요청과 일반 요청이 같은 배치에 섞였을 때 엔진이 비정상 종료되는 문제를 발견했습니다.

원인

vLLM 본체의 문법 마스크 함수가 구조화 요청 행만 골라낼 인덱스를 pin_memory=True 텐서로 만드는데, vllm-rbln은 샘플링과 마스크를 CPU 전용 torch로 처리해 pinned memory 할당자가 없었습니다. 배치가 전부 구조화 요청이면 인덱스를 만들지 않고 구조화 요청이 없으면 이 함수를 부르지 않아, 두 종류가 섞인 배치에서만 예외가 났습니다. vLLM v1은 엔진 루프의 예외를 치명적 오류로 처리해 API 서버까지 종료됐습니다.

해결

vLLM 파일은 고치지 않고, 서빙 런처가 import하는 런타임 패치로 그 모듈 안의 torch와 xgrammar 두 이름만 감쌌습니다. 텐서를 만들 때는 pin_memory 인자만 빼고, 그러면 xgrammar CPU 커널이 텐서 인덱스를 받지 못해 TypeError가 이어서 나므로 인덱스를 정수 리스트로 바꿔 넘깁니다. xgrammar는 처음 접근할 때 감싼 이름을 실제 모듈로 덮어쓰는 지연 로딩 모듈이라, 먼저 로드한 뒤 감쌌습니다.

결과

같은 버전으로 CPU에서 재현한 혼합 배치는 패치 전 예외가 났고, 패치 후에는 구조화 행에 허용 토큰만 남고 일반 행은 비트 단위로 그대로였습니다. 운영 서버에서 일반 2건과 구조화 3건을 섞어 혼합 decode 39스텝을 돌렸을 때도 5건 모두 200으로 응답했고, 구조화 요청은 스키마를 지켰습니다.

4-3호스트 CPU 포화로 생성 속도가 떨어짐

문제

EXAONE 3.5 7.8B를 서빙하던 때, 평소 약 48 tok/s이던 생성 속도가 8 ~ 11 tok/s로 떨어졌습니다.

원인

NPU가 아니라 호스트 CPU 문제였습니다. 워크스페이스 루트가 /로 잡힌 원격 VS Code의 ripgrep이 파일시스템 전체를 훑으며 CPU 32코어를 load 70 이상으로 포화시켰고, vllm-rbln은 decode의 토큰 샘플링을 CPU에서 하므로 그대로 느려졌습니다.

해결

ripgrep을 종료하고 워크스페이스 범위를 좁혔습니다.

결과

생성 속도가 약 48 tok/s로 돌아왔습니다. 같은 ripgrep 명령을 8개 띄워 재현하자 48.4에서 26.5 tok/s로 떨어졌고, 종료하자 48.3 tok/s로 돌아왔습니다.

추론 500 에러슬라이딩 윈도우용 블록 테이블 미전달텍스트 회귀 게이트
이미지 500 에러프롬프트에 이미지 자리 토큰 누락CPU 이미지 대화 게이트
해결

네 건 모두 NPU 없이 CPU에서 재현되는 호스트 코드 문제였습니다. 이후로는 서비스를 내리기 전에 CPU에서 원인을 재현하고 고친 뒤 CPU 게이트를 모두 통과시키는 순서를 지켰습니다.

결과

마지막 교체는 한 번에 끝났습니다.

4-5비전 인코더 복제 병렬화의 이득이 0

문제

새 이미지의 인코딩 지연을 줄이려고 비전 인코더를 다른 칩 다섯 개에 복제해 병렬로 돌리는 구조를 만들었습니다. 호스트 검증을 모두 통과했고 CPU 모의 실험에서는 4.9배가 나왔지만, 실제 NPU에서는 10장 13.59초로 기존 13.46초와 같았습니다.

원인

모의 실험은 sleep으로 대신해 GIL을 놓았지만, 실제 런타임 호출과 이미지별 마스크 생성은 GIL을 쥔 채 동기로 돌아 스레드가 직렬화됐습니다.

해결

NPU 메모리만 차지하는 복제 구조는 배포에서 뺐습니다.

4-6NPU에서 LSTM이 틀린 값을 냄

문제

회의록의 화자 분리 모델(pyannote)을 NPU로 옮길 수 있는지 검토하던 중, 단방향 LSTM이 컴파일과 실행은 되는데 결과가 틀렸습니다. 실제 크기(입력 60, hidden 128)에서 CPU 대비 코사인이 10프레임 0.559, 60프레임 0.007까지 떨어졌습니다.

원인

같은 크기의 linear, conv1d 대조군은 코사인 0.999997로 정확해, NPU 전체가 아니라 LSTM 고유의 문제로 좁혔습니다. hidden 8 ~ 16 크기에서는 코사인 1.0000이라 작은 예제로는 드러나지 않습니다. 양방향 LSTM이 컴파일 중 죽는 원인은 그래프 하나에 LSTM 모듈이 2개 이상 있는 것으로 따로 분리했습니다.

해결

LSTM이 들어간 화자 분리 세그멘테이션은 NPU로 옮기지 않았습니다.
