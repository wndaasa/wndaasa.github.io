01모델 구현

1-1토크나이저와 모델 구성

번역 방향 태그를 포함한 한영 공용 BPE 토크나이저(32k), 인코더-디코더 트랜스포머, 형태소 합성 인코더, minGRU 선형 순환 seq2seq, 학습 루프, 문서 단위 디코딩, CPU 서빙 서버를 작성했습니다.

1-2minGRU 병렬 스캔

선형 점화식을 로그 공간 병렬 스캔으로 구현해 학습은 병렬로, 추론은 KV 캐시 없이 O(1) 메모리로 돌게 했습니다. 병렬 스캔과 순차 계산의 결과가 최대 오차 1.6e-6으로 일치함을 테스트로 확인했습니다.

02학습

2-1OPUS 학습과 학술 도메인 적응

OPUS-100으로 학습한 뒤 학술 논문 데이터로 파인튜닝해, ko → en BLEU가 7.36에서 44.10으로 올랐습니다.

2-2같은 크기로 구조 비교

"같은 크기, 다른 구조"만 비교하도록 파라미터 수를 60,521,472 대 60,524,544로 맞추고, 같은 데이터, 같은 스텝, 같은 평가로 minGRU와 트랜스포머를 비교했습니다.

minGRU가 10번의 평가 내내 앞섰고 2만 스텝 val_loss는 4.15 대 4.36이었습니다. 길이 4,096 디코딩에서 메모리는 약 2.5배 적고 속도는 2.2배 빨랐으며, 실제 학습의 최대 메모리도 10.60GB로 트랜스포머의 16.26GB보다 작아 24GB GPU 한 장에서 문서 단위 학습을 할 수 있었습니다.

2-3문서 단위 번역

문장 구분자로 새 토큰을 만들지 않고 기존 종료 토큰을 재사용해 어휘와 임베딩을 그대로 살렸습니다. minGRU는 위치 임베딩이 없어서 최대 길이를 128에서 1,024로 늘려도 파라미터가 같았고, 문장 단위로 학습한 체크포인트를 문서 학습의 출발점으로 그대로 쓸 수 있었습니다.

268M 모델을 OPUS 1,699만 쌍으로 먼저 학습한 뒤, 논문 60,483편에서 만든 179,136개 윈도우로 이어 학습해 val_loss 0.906, 짧은 문서 20개 기준 문서 모드 BLEU 35.46을 얻었습니다.

03서빙

3-1CPU 서버와 모델 선택

외부 의존성 없는 CPU 서버에 일반용과 문서용 두 모델을 함께 올리고, 번역 방향과 입력 길이로 모델을 고르게 했습니다. 입력 길이 기준은 토큰 70개입니다. 문서 디코딩이 느린 긴 입력은 문장별로 나눠 타임아웃을 피했습니다. 같은 서버의 NPU 서비스가 쓸 호스트 CPU가 부족해지지 않도록 스레드는 8개로 제한했습니다.

04트러블슈팅

4-1학술 파인튜닝 후 일상 번역 능력을 잃음

문제

학술 도메인으로 파인튜닝하자 일상 대화 번역 품질이 크게 떨어졌습니다.

원인

새 도메인 학습이 기존 능력을 덮어쓰는 catastrophic forgetting이었습니다.

해결

일반용과 학술용 두 모델을 함께 쓰는 구성을 택했습니다.

4-2형태소 합성 인코더 가설 기각

문제

형태소 합성 인코더는 11번의 평가 모두 기준 모델보다 열세였고, 학습 속도도 1,150에서 225 ex/s로 떨어졌습니다.

원인

속도 저하는 ROCm 라이브러리가 가변 합성곱 배치마다 커널을 다시 탐색하기 때문이었습니다.

해결

품질과 속도 모두 이득이 없어 가설을 기각했습니다.

4-3val_loss는 낮은데 BLEU가 0.03

문제

문맥 학습 뒤 val_loss는 2.14였지만 BLEU는 0.03이었습니다.

원인

문장용 디코딩이 첫 종료 토큰에서 멈춰, 문서의 첫 문장만 번역하고 끝났습니다.

해결

입력 문장 수만큼 생성하고 멈추는 문서용 디코더를 따로 구현했습니다.
