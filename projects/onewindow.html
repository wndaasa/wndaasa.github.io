01검색 API 구축

현행 검색 시스템을 EXAONE, bge-m3, pgvector, MCP 구성으로 대체했습니다.
요청은 아래 순서로 처리됩니다.

1-1질의 의도 라우터

질의를 검색, 상세, API, 잡담 4가지로 나누는 프롬프트를 설계하고, vLLM의 structured outputs로 네 라벨 외의 토큰은 생성하지 못하게 막았습니다.

정답 라벨을 미리 붙인 단일 질의 156개 중 155개, 직전 질의가 있는 멀티턴 질의 30개 모두를 맞게 분류했습니다. 분류 한 건의 응답 시간은 평균 0.05초, p95 0.06초입니다.

API로 분류된 질의는 공공데이터포털 오픈API 호출 URL을 만들어 돌려줍니다. EXAONE은 대상 API와 파라미터만 JSON으로 내고, 서버가 오픈API 명세와 대조해 URL을 조립합니다. 서비스키는 LLM에 넘기지 않습니다.

1-2LLM 검색어 확장

EXAONE이 질의 하나에서 핵심어, 구, 전문용어, 조건어와 재작성 질의(query rewrite) 2개를 내면, 코드가 이를 조합해 키워드 최대 7개와 재작성 질의 최대 3개를 만듭니다. 키워드는 MCP 키워드 검색에, 질의 원문과 재작성 질의는 벡터 검색에 넘깁니다.

1-3키워드 검색 (MCP)

키워드 검색은 사내 MCP 플랫폼에 올라간 카탈로그 MCP 서버의 search_catalog_ranked 도구로 수행합니다. 키워드를 넣으면 제목, 키워드, 설명 순으로 가중치를 둔 관련도 순서로 상품을 최대 20건 돌려줍니다.

MCP 클라이언트는 SDK 없이 httpx로 작성했습니다. Streamable HTTP로 initialize, tools/list, tools/call을 처리하고, 게이트웨이 재시작으로 세션이 사라지면 세션을 새로 받아 다시 호출합니다.

키워드마다 MCP를 한 번씩 병렬로 호출하고, 같은 키워드의 결과는 10분 동안 캐시합니다.

외부 기관의 MCP 서버(도구 45개)도 챗봇에 연동했습니다. 질의가 이 기관의 조회가 필요한지는 검색어 확장 단계에서 함께 판정하며, 해당 주제 질의 8개를 모두 맞혔고 데이터셋 질의 136개를 잘못 넘긴 경우는 없었습니다.

1-4벡터 검색 (pgvector)

약 13만 건의 데이터를 bge-m3로 임베딩해 PostgreSQL pgvector(HNSW)에 적재했습니다. 질의 원문과 재작성 질의마다 상위 20건을 받습니다.

기존 벡터는 제목, 분류, 키워드, 설명을 이은 텍스트 하나를 HTML 태그가 섞인 채로 임베딩한 것이었고, 2,048토큰을 넘는 부분은 잘렸습니다. 이를 대신할 구성으로 정제한 다섯 필드를 하나로 이은 벡터, 다섯 필드 벡터의 가중합, 제목과 설명 두 벡터의 합성을 비교했습니다. 다섯 필드 가중합은 0.1 간격으로 합이 1인 1,001개 조합을, 두 벡터 합성은 0.05 간격의 비율을 탐색했습니다.

튜닝셋 100문항으로 고르고 시험셋 99문항으로 확인하니, 다섯 필드 가중합은 튜닝셋에서만 앞서고 시험셋에서는 이은 벡터와 동률이라 제외했고, 두 셋 모두에서 좋은 제목, 설명 0.5:0.5 합성을 택했습니다. MRR@20은 기존 벡터 대비 튜닝셋 0.830에서 0.850, 시험셋 0.736에서 0.754로 올랐습니다. 청킹은 토큰 분포와 순위 변화를 분석한 결과, 효과가 미미하다고 판단하여 적용하지 않았습니다.

무의미한 입력에는 빈 결과를 돌려주도록 임계값을 두었고, 무의미 질의 60개와 정상 질의 199개에서 임계값별 오판 수를 비교해 0.64로 정했습니다.

1-5RRF 결합과 LLM 재순위

키워드 검색과 벡터 검색 결과 목록을 가중 RRF(k=60)로 합칩니다. 벡터 검색은 질의 원문 결과에 2.0, 재작성 질의 결과에 1.0 가중치를 주고, 목록마다 상위 결과 일부는 반드시 후보에 넣습니다. RRF 상위 40건은 LLM이 목록 전체를 보고 순위를 다시 매깁니다.

1-6응답 스트리밍과 멀티턴

검색 결과와 AI 요약은 SSE로 스트리밍합니다. SSE는 HTTP 상태가 늘 200이라, 생성 중 실패는 오류 이벤트로 보내고 클라이언트가 연결을 끊은 경우와 구분해 기록합니다.

멀티턴에서는 직전 질의를 함께 보고 후속 질의를 해석합니다. "미세먼지 측정 데이터 찾아줘" 다음의 "무료인 것만 다시 보여줘"처럼 조건을 더하는 질의는 LLM이 조건을 해석하고, MCP가 돌려준 상품을 카탈로그 DB 속성으로 걸러 냅니다.

OWASP LLM Top 10 (2026) 기준으로 입력과 외부 자료 정제, 프롬프트 안 자료 경계 태그, 도구 인자 검증, API 키 인증, 개인정보 로그 마스킹을 반영했습니다.

1-7LLM 서빙 환경 구축

A100 80GB 2장 서버 한 대에 k3s 단일 노드로 vLLM을 올렸습니다. 컨테이너로 운영하고 작은 모델은 레플리카로 늘리기 위해 Docker 구성에서 옮겼습니다.

쿠버네티스의 GPU 공유 방식은 맞는 것이 없었습니다. time-slicing은 파드에 특정 GPU를 지정할 수 없고, MPS는 메모리를 균등하게 나누며, MIG는 조각이 너무 큽니다. 그래서 파드마다 NVIDIA_VISIBLE_DEVICES로 GPU를 고정했습니다. EXAONE-4.0-32B-AWQ는 단일 인스턴스를 TP2로 두 장에 나눠 올리고, bge-m3는 GPU마다 레플리카를 하나씩 두었습니다.

KV 캐시는 gpu-memory-utilization 비율 대신 바이트로 지정했습니다. 비율은 기동할 때 남은 메모리를 기준으로 잡혀서, 같은 GPU에 여러 모델을 띄우면 KV 크기가 흔들립니다. EXAONE의 최대 컨텍스트는 128K(131,072 토큰)입니다. 기동 로그로 잰 토큰당 KV 크기가 GPU당 약 38.9KB라, KV 캐시를 GPU당 10GiB로 지정해 약 27만 토큰(275,855)을 확보했습니다.

같은 모델의 투기 디코딩 실험과 vLLM 패치는 32B 서빙 최적화 페이지에 정리했습니다.

1-8요청 단위 trace 로그

요청마다 trace_id를 발급해 응답 헤더 X-Trace-Id로 돌려주고, 요청이 끝나면 성공과 실패 모두 JSON 한 줄로 날짜별 JSONL 파일에 남깁니다. 검색 API와 품질 점검 API에 같은 형식으로 적용했습니다.

한 줄에 LLM 단계별 토큰과 지연, MCP와 임베딩 호출의 성공 여부와 재시도 횟수까지 담아, 엔드포인트별 성공률, 응답 시간 p95, MCP 호출 실패 수를 jq 한 줄로 추출합니다.

기록 전에 주민등록번호, 카드번호, 전화번호, 이메일 형태 문자열을 가리고, 오픈API 호출 인자는 인증키 때문에 남기지 않습니다.

1-9검색 품질 평가

hit@1, hit@3, F1@3, nDCG@3, 처리 시간으로 채점 스크립트를 만들고, 검색 파이프라인 튜닝에 쓰지 않은 시험셋 99문항으로 현행 검색 시스템과 비교했습니다. AI 검색 hit@1은 56개에서 82개로 올랐고, 목록을 받기까지의 평균은 현행 13.6초, 고도화 3.7초이며 재순위 결과까지 포함하면 5.2초입니다.

1-10부하 측정

동시 요청 수별로 검색 요청부터 답변 스트리밍이 끝날 때까지의 p95를 재서 동시 처리 상한을 정했습니다. 측정할 때는 vLLM 프리픽스 캐시 효과를 무작위 프롬프트로 제거하고, 같은 GPU를 쓰는 다른 작업에 오염된 표본은 분리해 부트스트랩 2,000회로 95% 신뢰구간을 냈습니다. 동시 4건에서 8건으로 늘리면 처리량은 초당 0.43건에서 0.54건으로 25% 느는 데 그치고 답변 완료 p95는 12.4초에서 23.2초로 구간이 겹치지 않게 늘어, 상한을 4로 정하고 세션별 요청 한도도 두었습니다.

02카탈로그 품질 자동 점검 API 구축

원윈도우 카탈로그의 상품 메타데이터는 각 플랫폼에서 수집됩니다. 현행 품질진단은 플랫폼이 판정한 결과를 저장만 하고 적용 규칙도 이름 길이 2건뿐이라 빈 값이나 원천 페이지와 다른 값을 걸러 내지 못했고, 랜딩 페이지 점검은 주기 실행과 조회 화면 없이 API를 직접 호출해야 했습니다. 원천 페이지를 크롤링해 DB 값과 대조하고, 관리자가 승인한 수정값만 반영하는 API를 만들었습니다.

2-1원천 페이지 크롤링

상품마다 등록된 랜딩 URL의 페이지를 httpx로 가져옵니다. 주소 형식 오류, 접속 실패, 상세 페이지가 아닌 경우, 다른 페이지로 이동한 경우는 랜딩페이지 오류로 기록하고, 이동한 페이지의 값은 대조와 제안에 쓰지 않습니다.

2-2페이지 값 추출

추출 방식은 두 가지입니다. 규칙 방식은 HTML 마크업을 파싱하고, LLM 방식은 본문 텍스트를 EXAONE이 JSON으로 추출합니다. 이후 대조 로직은 같습니다.

2-3DB 대조와 점검 유형

유형방식잡는 것
01 결측규칙상품명, 설명, 키워드, 생산기관명, 서비스유형, 갱신주기, 랜딩 URL이 비어 있음. 파일형 상품의 파일 형식 누락
02 이상값LLM상품명, 설명, 키워드, 생산기관명에 쓸 수 없는 값
03 랜딩페이지규칙접속 실패, 상세 페이지 아님, 다른 페이지로 이동, 추출 실패
04 값 불일치대조서비스유형, 상품명, 생산기관명, 설명, 키워드, 갱신주기, 파일형식이 페이지와 다름. 페이지 값을 수정값으로 제안

2,000자가 넘는 설명은 잘라서 판정하므로 수정값을 제안하지 않습니다.

2-4점검 회차와 수정값 반영

점검은 오래 걸리기 때문에 실행 요청은 회차만 만들고 바로 응답한 뒤, 점검은 백그라운드에서 진행합니다. 진행 상황과 결과는 회차 단위로 조회하고 중간에 멈출 수 있습니다.

결과마다 발견값, 사유, 제안값이 붙고, 관리자가 승인한 제안값만 상품 테이블에 반영합니다. 공공데이터포털 상품 100건 표본은 규칙 추출 모드로 54초에 결측, 이상값, 값 불일치 후보 162건을 찾았고, 원천 페이지 값으로 수정값 후보 138건을 제안했습니다.

03트러블슈팅

3-1MCP 게이트웨이 429로 키워드 검색 누락

문제

부하 측정 중 동시 요청 4건에서 키워드 검색의 25.8%가 429로 빠졌습니다.

원인

MCP 게이트웨이는 서버별 동시 처리 한도 10건을 넘으면 기다리게 하지 않고 바로 거절합니다.

해결

프로세스 전체의 MCP 동시 호출을 8건으로 묶고, 한도 초과로 받은 429만 지수 백오프로 최대 3번 재시도하게 했습니다. 그래도 실패한 키워드만 빈 결과로 두고 검색은 계속합니다.

결과

동시 2, 4, 8건 부하 측정에서 키워드 검색 실패는 0건이었습니다.

3-2keep-alive 경쟁 조건으로 인한 간헐적 500 에러

문제

부하 측정 중 임베딩 호출 1,275건 중 1건에서 500 에러가 났습니다.

원인

httpx 클라이언트와 vLLM 서버의 keep-alive가 둘 다 5초라, 서버가 먼저 닫은 연결을 클라이언트가 재사용했습니다. 연결을 4.996 ~ 4.999초 쉬게 했을 때만 16번 중 8번 재현돼 원인을 확정했습니다.

해결

클라이언트 keep-alive를 4초로 줄이고, 연결 오류는 1번 재시도하게 했습니다.

결과

같은 구간에서 44번 모두 성공했습니다.

3-3구조화 출력 JSON 잘림

문제

검색 대상 판단이 전부 none으로 나오고, 조건 해석 단계는 질의에 없는 필터 값을 지어냈습니다.

원인

JSON 스키마의 키 5 ~ 9개를 전부 required로 강제하자, 모델이 쓰고 싶지 않은 키 앞에서 공백만 생성하다 max_tokens에 걸려 JSON이 잘렸습니다.

해결

required를 최소로 줄이고 값 검증은 코드로 옮겼습니다. 파싱에 실패하면 스키마 없이 1번 다시 호출합니다.

3-4벡터 동기화 지연

문제

카탈로그 변경을 벡터 DB에 반영하는 동기화 한 주기가 994초 걸렸습니다.

원인

DB가 en_US.utf8 정렬 규칙이라 긴 한글 텍스트 컬럼의 ANALYZE가 느렸습니다. 문서 컬럼 423초, 설명 컬럼 240초였습니다.

해결

VACUUM ANALYZE를 VACUUM으로 바꿨습니다.

결과

한 주기가 282초로 줄었고, 남은 시간은 대부분 Materialized View 갱신입니다.

3-5LLM 추출값이 페이지 원문과 다름

문제

LLM 추출에서 확장자에 오픈API 출력 형식(XML, JSON)이 섞이고, 키워드의 띄어쓰기를 바꾸거나 잘린 키워드를 채워 넣었습니다. 같은 30페이지에서 규칙 추출과 확장자가 22건 중 9건만 일치했습니다.

해결

프롬프트를 보강하고, 페이지 원문에 그대로 있는 값만 받도록 코드에서 검증했습니다. 확장자는 '확장자' 라벨 다음 줄의 값만 씁니다.

결과

6개 항목이 모두 규칙 추출과 일치했고, 30페이지 LLM 추출 시간은 80초에서 47.5초로 줄었습니다.

3-6개발용 Qwen의 한자, 가나 혼입

배경

외부로 보낼 수 없는 납품 소스를 다룰 때는 같은 GPU 서버에 올린 Qwen3.8-27B를 Claude Code의 모델로 붙여 개발했습니다. 서비스에는 쓰지 않는 개발 전용 모델입니다.

문제

답변에 한자와 가나가 섞여 나왔고, 프롬프트 지시, presence_penalty, temperature 조정으로는 막히지 않았습니다.

해결

vLLM logits processor를 작성했습니다. 기동할 때 어휘 248,077개를 전부 디코딩해 한자나 가나가 든 토큰 58,909개와, 한자나 가나로만 완성되는 UTF-8 바이트 조각 토큰 336개를 고르고, 생성 단계마다 이 59,245개 토큰의 logit을 -∞로 바꿉니다. 한글 선두 바이트로 시작하는 조각은 막지 않게 해 차단 목록에 한글이 든 토큰은 0개입니다.

한계

vLLM은 logits processor와 투기 디코딩을 함께 쓸 수 없어, MTP를 끄면서 생성 속도가 TP=1 기준 65에서 48 tok/s로 내려갔습니다.

3-7개발용 Qwen의 프리픽스 캐시 미스

문제

7일 동안 1,675건, 평균 6만 토큰 프롬프트에서 평균 첫 토큰 지연이 19.5초, 프리픽스 캐시 적중률이 31%였습니다.

원인

Claude Code는 대화 중간에 system 메시지를 넣는데, vLLM의 Anthropic API 어댑터가 이를 맨 앞 system 프롬프트에 이어 붙였습니다. 이어 붙는 내용이 요청마다 달라 system 프롬프트 끝이 매번 바뀌고, 그 뒤 대화 전체가 캐시에서 빗나갔습니다.

해결

중간 system 메시지를 같은 자리의 user 메시지로 바꾸는 ASGI 미들웨어를 서버 앞에 두었습니다.

결과

실사용 126건, 평균 6.6만 토큰에서 적중률 97.6%, 평균 첫 토큰 지연 0.83초가 됐습니다.
