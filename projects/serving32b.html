32B 서빙 최적화

원윈도우 사업에 들어가기 전 두 달 동안, A100 한 장에서 32B 모델로 웹 검색 에이전트 채팅 서비스를 만들며 응답 속도와 출력 안정성을 끌어올렸습니다.

기간
2026.07 ~ 08 (원윈도우 착수 전 사전 실험)
역할
A100, H100 환경의 서빙 설정, vLLM 패치, 앱, 벤치마크, 분석 단독 수행
환경
A100 80GB 1장 (CUDA 12.4 드라이버 제약), 비교 벤치용 H100
기술
vLLM 0.15 (awq_marlin), EXAONE-4.0-32B-AWQ, EXAONE-4.0-1.2B (draft), FastAPI, React
9 → 156 TPS단일 사용자 생성 속도, 코드 기준
~40ms첫 토큰 지연
72.6 ~ 83.1%실서비스 draft 토큰 수락률
2건vLLM 소스 패치, 1건은 업스트림에 같은 수정 머지

OVERVIEW단계별 생성 속도

주 용도가 도구 호출로 정해진 뒤, 지연을 줄이는 것과 32B 에이전트의 환각과 형식 이탈을 줄이는 것을 목표로 잡았습니다. 아래는 단일 사용자 기준 초당 생성 토큰 수입니다.

01vLLM 소스 패치 2건

패치 1

draft 모델을 붙이자 코드 55, 문장 29 TPS로 n-gram보다도 느려졌습니다. 원인은 draft 모델이 CUDA 그래프를 쓰지 않고 매 스텝 eager 모드로 돌던 것이었고, 그래프 초기화 조건에 draft 모델 여부를 넣어 고쳤습니다. 이후 업스트림에 같은 수정이 머지됐습니다(PR #47460, 0.19.0까지 미반영).

패치 2

배치 1에서 프리픽스 캐시가 완전히 적중하면 엔진 프로세스가 죽었습니다. draft 모델의 Triton 커널이 특정 인자를 상수로 특수화해서 생긴 문제로, 그 인자를 특수화 대상에서 빼서 해결했습니다.

제약

A100 서버 드라이버가 CUDA 12.4라 최신 vLLM을 쓸 수 없어 0.15로 고정하고 버전 제약을 문서화했습니다. EXAONE 4.0의 하이브리드 슬라이딩 윈도우 어텐션이 draft 투기 디코딩을 지원하지 않는 문제는 KV 캐시 관리자 설정을 바꿔 우회했습니다.

02출력 안정성

형식

직접 정한 JSON 도구 호출 형식에서 모델이 자주 벗어나, 모델이 학습한 고유 도구 호출 형식으로 바꿨습니다.

사고 태그

사고 구간이 닫히지 않고 끝나는 문제를 logit lens로 보니 종료 토큰 확신이 99.2%였습니다. 샘플링 조정으로는 못 고친다고 판단하고, 사고 단계를 먼저 끊은 뒤 이어서 답을 생성하는 2단계 구조로 바꿔 구조적으로 막았습니다.

환각

bf16과 AWQ를 20~30회씩 비교해 이름 변형과 태그 미닫힘은 양자화와 무관하고, 가짜 URL만 AWQ에서 더 잦다는 것(25% 대 5%, 시사적)을 분리했습니다. 사고 단계에만 presence penalty를 1.5로 주면 이름 변형이 83%에서 53%로 줄었습니다(N=30, p≈0.01).

프롬프트로 막을 수 있는가. J-lens로 URL을 지어내는 지점을 보니 시스템 프롬프트의 기여가 오히려 음수(-3.6)였습니다. 프롬프트에 "지어내지 마"를 더 쓰는 것보다 근거 검증 게이트 같은 구조적 차단이 맞다고 판단했습니다.

03하드웨어 벤치마크

같은 스크립트를 A100과 H100에서 돌려 비교했습니다(입력 1024, 출력 256 토큰, 투기 디코딩 끔).
